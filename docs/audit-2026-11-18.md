## Приоритетные находки

### A01 · P1 · Прежний владелец Discord сохраняет полномочия

Источники: `backend/app/services/auth.py:267`, `:291–302`; `backend/app/services/discord_roles.py:324–331`; `_active_membership()` в auth.py.

`claim_guild()` выдаёт OWNER новому подтверждённому владельцу, но не снимает OWNER со старого. Синхронизация ролей пропускает существующего OWNER; выход с сервера/отсутствие ролей также не деактивирует такое членство. Поэтому прежний владелец может сохранять управление и после нового входа. Это отдельная проблема от срока жизни JWT.

Исправление: определить правило единственного Discord-владельца, сверять его с текущим владельцем guild, понижать/деактивировать прежнего и отзывать его сессии. Проверка: передача владения A → B, повторный вход A, попытка административного запроса; отдельно выход A с сервера.

### A02 · P1 · OAuth state не связан с браузером

Источники: `backend/app/api/v1/auth.py:250–263`, `:278–301`; `backend/app/services/discord_oauth.py:129–158`.

Login создаёт подписанный state, но не сохраняет секрет инициировавшего браузера. Callback проверяет подпись/срок, а не принадлежность этого входа браузеру. Это создаёт login-CSRF: чужая ещё не использованная callback-ссылка может установить сессию чужой учётной записи в браузере получателя. Не утверждается возможность повторного использования уже погашенного Discord code.

Исправление: одноразовый state, связанный с короткоживущей HttpOnly cookie/серверной сессией; проверка совпадения и потребление nonce. Подход сверён с RFC 9700, §2.1 и §4.7.1: https://www.rfc-editor.org/rfc/rfc9700.html . Проверка: callback из браузера B со state браузера A должен быть отклонён.

### A03 · P1 · Изменение прав не отзывает действующий JWT

Источники: `backend/app/api/deps.py:101–123`; `backend/app/core/security.py`; `backend/app/api/v1/clan_roles.py`.

Principal берётся из JWT. Есть проверка чёрного списка для части пользователей, но нет проверки актуального активного членства, роли и scope. Ограничение роли/деактивация членства не гарантируют немедленный отзыв доступа; OWNER исключён из проверки blacklist. В Settings TTL по умолчанию равен часу, но отслеживаемый `infra/render.yaml:50–54` задаёт ACCESS_TOKEN_TTL_MIN=10080, то есть 7 суток. Реальное значение в работающем сервисе не проверено; при таком blueprint старые права могут сохраняться до недели.

Исправление: версия авторизации/сессии либо проверка текущего членства с управляемым кешем; инвалидировать при изменении прав. Проверка: получить токен → отозвать право → повторить запрещённый запрос тем же токеном.

### A04 · P1 · Запуск тестов способен удалить рабочие таблицы

Источники: `backend/tests/conftest.py:8–11`, `:40–43`.

`setdefault(DATABASE_URL, test_url)` сохраняет адрес из окружения вызывающего процесса. Затем fixture выполняет metadata.drop_all/create_all. Если перед pytest экспортирован адрес staging/production, тесты используют его. Факт потери данных в текущей среде не установлен; опасный путь подтверждён.

Исправление первым отдельным изменением: обязательный TEST_DATABASE_URL, защита от совпадения с runtime URL, изолированная база на запуск, fail-closed перед любым drop. Не полагаться только на слово test в имени.

### A05 · P1 · Старый Compose-путь не собирает и не запускает систему

Источники: `infra/Dockerfile.api:12–13`, `:29`; `infra/docker-compose.yml:29–32`; `frontend/next.config.ts:6`; `backend/app/core/config.py`.

Dockerfile копирует отсутствующий backend/alembic вместо migrations. Установка pyproject не устанавливает runtime-зависимости, так как они не объявлены в project. В окружении API нет обязательного JWT_SECRET. Frontend proxy по умолчанию компилируется на localhost:8000, тогда как API расположен в другом контейнере; runtime NEXT_PUBLIC_API_URL не исправляет уже собранный proxy.

Исправление: выбрать один актуальный локальный путь и один production-путь; восстановить сборку/запуск на чистом checkout. Это дефект старого пути, а не доказательство поломки корневого production Dockerfile.

### A06 · P2 · Личные планы/черновики доступны следующему пользователю браузера

Источники: `frontend/src/features/planning/model/plan.ts:63–67`, раздел snapshots; `frontend/src/entities/report/index.ts:237–239`; `frontend/src/features/cabinet/model/session-context.tsx:49–54`.

Планы, снимки и черновик используют общие localStorage-ключи. Logout сбрасывает session, но не эти данные. При смене пользователя/клана на одном браузере остаются сведения предыдущего пользователя. Это локальное смешивание контекстов, а не доказанная утечка серверной БД между кланами.

Исправление: namespace userId+clanId, очистка чувствительного состояния при смене сессии, осторожная миграция существующих локальных данных без их молчаливой потери.

### A07 · P2 · Retry возвращает удалённый объект плана

Источники: `frontend/src/features/planning/model/clanPlan.ts:84–102`, `:110–113`; `backend/app/api/v1/clan_plan.py:95–100`.

Сценарий: отправка upsert ещё в полёте → пользователь очищает план → старая отправка падает → catch добавляет старый upsert в очередь, несмотря на новый clear. Сервер очищает список и тут же добавляет этот объект. Минимальное исполнение алгоритма в Node подтвердило `{clear:true,upsert:[{id:'old'}]}`.

Исправление: свежий clear должен отменять более старые операции; определить порядок поколений очереди. Проверить clear, delete, upsert, ошибку и повторную доставку в разных сочетаниях.

### A08 · P2 · Параллельные отклики на операцию перезаписывают друг друга

Источники: `backend/app/api/v1/operations.py:84`, `:204–211`; `backend/app/services/operation_plan.py:71–100`.

Операция читается без row lock, участники хранятся JSON-списком и полностью перезаписываются. Два пользователя читают одинаковое состояние, последний commit теряет ответ первого; проверка лимита роли также работает по устаревшему списку. Аналогичный риск есть для JSON-снимков/планов операции.

Исправление: блокировка на изменение, optimistic version либо нормализованная таблица участников. Нужен конкурентный тест с двумя отдельными сессиями PostgreSQL.

### A09 · P2 · Временный сбой отправки навсегда теряет уведомление

Источник: `backend/app/services/notify_dispatch.py:79–108`.

delivered_at присваивается до успешной доставки. Ложный результат Discord, 429/500 push не препятствуют commit. Следующий проход исключает такую запись. При этом письмо на сайте может оставаться доступным: находка относится к внешней доставке.

Исправление: статусы отдельно по каналу, ограниченные retry/backoff, идемпотентность, различение окончательной и временной ошибки. Проверить 429, 500, timeout и частичный успех каналов.

### A10 · P2 · Push принимает произвольный HTTPS endpoint

Источники: `backend/app/api/v1/notify.py:39`, `:76–82`; `backend/app/services/notify_dispatch.py:61–69`, `:100–101`.

Валидация проверяет лишь https-префикс. Сохранённый endpoint передаётся webpush без явного timeout. При включённом VAPID и отправке уведомления возникает поверхность SSRF и риска задержки фонового цикла. Достижимость внутренних адресов и успешная эксплуатация не проверены.

Исправление: проверка назначения push-службы/адресов, запрет внутренних направлений и опасных redirect, явный timeout, лимит времени/количества на проход. Не заявлять защиту до тестов фактического исходящего HTTP-клиента.

### A11 · P2 · Повторный Enter может создать несколько заказов

Источник: `frontend/src/entities/report/ui/SendOrderDialog.tsx:56–58`, `:81`.

submit не проверяет in-flight, поле продолжает обрабатывать Enter, хотя кнопка отключается через busy. При медленном ответе повторное нажатие запускает несколько POST. Исправление: синхронный ref-guard, блокировка повторной отправки; для устойчивости к retry — серверный idempotency key.

### A12 · P2 · После удаления вклада внешние показатели устаревают

Источники: `frontend/src/features/reports/ui/ReportProgress.tsx:46–48`, `:134`; `frontend/src/features/reports/ui/OrderCard.tsx:42`, `:190–193`.

Добавление вызывает callback перезагрузки внешнего report, удаление обновляет только локальный progress. Процент/счётчики/лента снаружи остаются старыми. Не приписывать этому автоматическое переоткрытие завершённого заказа: backend не обязан менять статус при удалении вклада.

Исправление: общий путь обновления/инвалидации данных после обеих мутаций; браузерная проверка согласованности карточки и списка.

### A13 · P2 · Ошибка загрузки выглядит как бесконечная загрузка

Источник: `frontend/src/features/reports/ui/ReportProgress.tsx:24–29`.

catch сбрасывает progress в null, а null всегда отображает Loading. Нет отдельного состояния ошибки и повторной попытки. Исправление: loading/error/data, retry, сохранение последних данных при временном сбое. Прямое применение идеи наблюдаемости из ролика.

### A14 · P2 · PATCH смешивает отсутствующее поле и null

Источники: `backend/app/schemas/order.py:31–35`; `backend/app/services/orders.py:89–96`; `backend/app/schemas/timer.py`; `backend/app/services/timers.py:137–155`.

OrderUpdate принимает явные null для обязательных полей, затем update присваивает их NOT NULL столбцам. Проба модели подтвердила приём title/quantity/produced=None; реальная DB-ошибка не воспроизводилась. Одновременно timer stockpile_id=null игнорируется, поэтому связь нельзя очистить этим PATCH.

Исправление: различать omitted/null; null запрещать обязательным полям, применять nullable-связям. Проверить ожидаемые 4xx и очистку склада.

### A15 · P2 · Нет автоматической проверки приложения при изменениях

Источники: `.github/workflows/wiki-sync.yml`; `frontend/package.json`; локальный запуск lint.

Единственный workflow обновляет wiki-данные и проверяет синтаксис JSON. Нет PR/push-gate для pytest, миграций, typecheck/build; frontend-тестов нет. next lint требует первоначальной настройки. Конфиг ESLint лежит внутри shared/api и импортирует отсутствующий в package.json boundaries-плагин.

Исправление: CI с отдельным PostgreSQL, безопасными тестовыми переменными, миграциями с нуля, pytest, typecheck, неинтерактивным lint и build. Добавить несколько сквозных браузерных сценариев, а не тесты на каждую строку реализации.

Исправление: короткая проверенная инструкция чистого запуска, карта актуальных модулей, пометка superseded для устаревших ADR, конкретные команды проверки. Не удалять историю решений без объяснения замены.

### A19 · P3 · История браузера не отражает навигацию по разделам

### A20 · P3 · Очистка процессов при сбое startup ненадёжна

Источник: `deploy/start.sh:4`, `:16–22`, `:29–32`.

При set -e ненулевой wait -n завершает shell до явного kill соседнего процесса; health-wait завершает Python с нулём даже после исчерпания попыток. Это дефект управления процессами, не подтверждённый production outage: оставшиеся процессы может завершить контейнерная среда.

Исправление: явный обработчик завершения/EXIT, сбор статуса без преждевременного выхода, ожидание graceful shutdown; health-wait должен падать при недоступном API.

## Архитектура и производительность: наблюдения без измерений

- Явные clan-scoped сервисы, ORM-фильтры/guards, проверки parent-связей, issuer/audience/expiry JWT, row-lock для добавления вкладов и единый API client — полезная основа. Подтверждённой серверной cross-clan read-утечки за этот проход не найдено; это не исчерпывающий тест изоляции.
- Практически все workspace импортируются синхронно в клиентском page.tsx. Кандидат на разделение JS по разделам; величина выигрыша не измерена. Не выдавать это за установленный плохой Core Web Vitals.

- Историческая `backend/migrations/versions/0010_reset_clan_data.py` намеренно выполняет TRUNCATE клановых/пользовательских данных. `deploy/start.sh` автоматически запускает upgrade head. Если возвращаться к базе с ревизией ниже 0010, этот шаг потенциально удалит её данные: сначала определить ревизию и проверить backup/restore на копии. - Контраст, адаптивность, реальные клики, производительность карты, загрузка на слабом телефоне и внешние интеграции требуют второго прохода на доступном локальном стенде.
